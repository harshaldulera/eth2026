# Siege onboarding — vault owners and guards, then agents

## Context

Siege has no onboarding. Only `scripts/seed.ts` creates vaults; there is no SDK package; one global `OWNER_SECRET` gates every owner action; every paid op from the browser is paid by, and pays out to, the arena's demo wallet; attack strategies are scripted, so no attacker burns compute; every guard thinks on the arena's 0G key. The product plan promises three things the code can't do yet: another team publishes their agent as a guard in three minutes, a red teamer runs units funded from their own wallet, and any outside agent attacks or guards through an API.

Dhruv's decisions (2026-11-06):
- **Part 1** = vault owners and their guards (hosted first, SDK next). **Part 2** = agents joining from outside: guard agents via an SDK (2A) and attacking agents, hosted units and bring-your-own (2B).
- Owners and red teamers identify and fund with their **own Hedera wallet** through a memo transfer (no wallet-connect library; a HashConnect pre-fill button is an optional extra).
- **Compute credits belong to the user.** Every published guard and every red teamer's unit thinks on the owner's own 0G credits, and the owner's balance visibly goes down. The arena key serves only the seeded fixtures and the referee.
- Red teamers' units pay op fees from their own balance; payouts land in the unit; the arena fronts nothing beyond the account-creation fee.
- Nothing changes in `SiegeVault.sol`: `createVault` stays arena-only, so the arena fronts the on-chain pot after the owner's deposit lands.
- We build all of it. No schedule or cut line lives in this plan; Dhruv manages time.

Verified facts the plan rests on: mirror-node transfers carry `memo_base64`, `transfers[]` and `transaction_id = payer-sec-nanos` (checked live); `validProtectedTool` accepts any 1–64-byte name; `businessAgent(castleId)` already makes `systemPrompt` return the orders verbatim and the verifier recompute exactly that; `fundVault(castleId, {potTinybar, durationSec})` and `chain.createTopic` are reusable as-is; the siege engine marks `open` only on a call to `castle.protectedTool`; `lib/db` runs WAL with `busy_timeout 5000`, so the Next process and the worker can share a queue table; `lib/proxy/zg.ts` already has `Billing = {kind:"team"} | {kind:"user", userId, apiKey}`. 0G facts (bounty page + router docs): users sign in at pc.0g.ai through Privy social login; iAI holders get 1.271 credits per staked iAI daily at 00:00 UTC and unused credits lapse; the bounty bonus is for apps where users "sign in with their 0G account and spend their own daily credits" with the balance visibly dropping; the router has `sk-` API keys (inference, billed to that user, denied on `/v1/account/*`) and `mk-` management keys with scopes (`account:read` → `GET /v1/account/*`; `keys:create` → `POST /v1/api-keys`; `keys:manage` → `PATCH|DELETE /v1/api-keys/:id`); there is no third-party "sign in with 0G".

## The journeys this must deliver (what the audience sees)

**J1 · Publish your agent as a guard (owner, hosted).** Grid → PUBLISH → GUARD: name, blurb, voice, secret orders, tools (the one protected tool marked) → CONNECT 0G: paste the key from pc.0g.ai, LED flips to `0G CONNECTED · <balance> credits` → MONEY: fee, pot, days, optional paying account → GO LIVE: a panel with the arena account QR, memo and amount; the owner sends from HashPack; `WAITING FOR DEPOSIT` → `SETTING UP 1/3 → 2/3 → 3/3` → stamp `YOUR VAULT IS LIVE`, share link + QR, owner key shown once. The vault appears on the Grid with its own portrait, tools and real owner wallet on Arkiv. An op against it shows the guard thinking on the owner's credits; the owner panel shows credits dropping and the fee cut earned on chain.

**J2 · Plug in your running agent (owner, SDK).** Same PUBLISH page, branch PLUG IN MY RUNNING AGENT → CONNECT 0G → an install snippet with the real guard key → the owner runs three lines on their laptop → the strip lights up CONNECTED → SELF-CHECK → SMOKE OP 1/3 2/3 3/3 → VERIFIED → fund (deposit panel) → GUARDING. An op from the browser is answered by the owner's process; killing the process turns the vault OFFLINE within 30 s and refunds live ops; restarting it brings GUARDING back. A real break pays out because the harness's model calls went through our proxy on the owner's credits.

**J3 · Run your own red-team unit (red teamer).** AGENTS → NEW UNIT: callsign, strategy preset or free text, caps → CONNECT 0G → deposit panel (memo, amount from their wallet) → `UNIT FUNDED`, operator key shown once → DEPLOY on a vault → the unit writes its own attack messages with the red teamer's credits, pays each op fee from its own account, and shows BALANCE and credits burning on its card → a cap hit radios the pager; APPROVE on a budget ask shows another deposit; on a policy cap it just raises the cap → a breach lands the payout in the unit → WITHDRAW sends it back to the wallet that funded it.

**J4 · Type ops yourself from your own money (red teamer).** With a unit in the browser, RUN OP on any vault is paid from that unit (not the arena's demo wallet), so the payout is the red teamer's. Without one, the demo wallet path stays for QR visitors and recon.

**J5 · Attack from your own agent (developer).** Recon briefing → BRING YOUR OWN AGENT ▶ → `/docs` → `node examples/raid-bot` with a Hedera account: lists guarding vaults, pays the 402 over x402, sends five messages with its turn token, prints the replay link; the payout goes to its own account. Nobody can hijack its turns, and free recon can't be farmed.

**0G connectivity** `lib/zg/connect.ts`:
- `connectZg({key})`: `mk-` → `GET /v1/account/*` (balance, usage) and `POST /v1/api-keys {name: "siege:<castleId|agentId>"}` to mint a dedicated `sk-` for that guard or unit; `sk-` → `GET /v1/models` probe only (bills them, no balance shown). Returns `{kind, balance?, models, inferenceKey}`; errors `unauthorized | needs_keys_create | unreachable`. `revokeZg(entity)` on vault close / unit stop (`DELETE /v1/api-keys/:id`, best effort).

Shown as `0G CREDITS <balance> · N calls · $X.XX` on the vault owner panel, the unit card, and live in the op room header when the op belongs to a connected unit or the vault is a published guard, so the audience watches the balance drop during an op.

Required for every published guard and every operator-funded unit; no silent fallback to the arena key. The SDK harness's calls bill to the castle's key, so a plugged-in team burns its own credits.
- UI piece `components/money/zg-connect.tsx` (shared by publish, plug-in and new-unit): key field, `POST /api/zg/validate` (probe only, never stores or mints), LED `0G CONNECTED · <balance> credits · <model>`, copy "Sign in at pc.0g.ai, create a management key (account read + create keys) and paste it. Your own daily credits pay for the thinking; we mint one key just for this and show your balance going down. An sk- key works too, without the balance."

**Keys** `lib/auth/keys.ts`: `newKey(prefix)` = prefix + 24 random base64url chars, `hashKey = sha256`. `ok_` (castle owner) and `rk_` (unit operator) stored hashed; `gk_` (guard) and `vk_` (vault/proxy) stored raw on the castle row. `app/api/_lib/http.ts` gains `isOwnerOf(req, castleId)` (global secret OR cookie `siege_owner` hash = `castles.owner_key_hash`), `requireOwnerOf`, `readOperatorKey(req)` (`x-siege-operator-key`, comma list allowed), `unitAccess(req, agentRow)`. `POST /api/owner` accepts `ok_` keys (hash lookup) and keeps setting the same httpOnly cookie, so `useOwnerGate`, the vault page and the pager keep working.

**Deposits** `lib/pay/deposits.ts` + `worker/deposits.ts` (+ one pass in `worker/tick.ts`):
- `createIntent({kind, refId, amountTinybar, payerFilter?, windowMin=45})` → `{intentId, code, memo: "siege:<code>", to: HEDERA_OPERATOR_ID, amount}`; code = 8 chars from `abcdefghjkmnpqrstuvwxyz23456789`.
- Worker every 5 s while any intent is open: `accountTransfers(operatorId, {sinceMs})` (new in `lib/chain/mirror.ts`: `GET /api/v1/transactions?account.id=&transactiontype=CRYPTOTRANSFER&result=success&timestamp=gte:&order=asc&limit=100`, follows `links.next`); pure `matchDeposits(intents, transfers)`: memo trimmed/lower-cased must equal `siege:<code>`, payer = `transaction_id` prefix, amount = the positive transfer to the operator, `payer_filter` respected, tx ids counted once. Sum ≥ amount → claim `awaiting|underpaid → funding` atomically, call the kind's handler (`onDepositConfirmed(kind, fn)` registry); under → `underpaid` with `received`; past `expires_at` → `expired` (money arriving within 24 h still funds, then `note` for manual refund); handler failure → `failed` + `error`, retried with backoff.
- Stub mode: `createIntent` confirms inline with payer `0.0.stub-owner-<code>` and a stub tx, so `npm run demo`, qa scripts and tests need no worker.
- UI piece `components/money/deposit-panel.tsx`: QR of the **arena account id** (HashPack's scanner reads a bare id; no `hedera://` scheme exists), three COPY rows (SEND TO / MEMO (required) / AMOUNT), blinking `WAITING FOR DEPOSIT`, countdown, `usePolling` of the status route every 3 s; states underpaid / funding (`SETTING UP k/n`) / failed / expired (NEW DEPOSIT WINDOW). Shared by J1, J2, J3 and top-ups.

## 1. Part 1 — vault owner + hosted guard (`/publish`, J1)

**Flow:** form → `POST /api/castles` → `{castleId, ownerKey (once), deposit, shareUrl}` + `Set-Cookie siege_owner=ok_…` → owner pays from any wallet → worker handler `fundVaultFromDeposit`: insert castle row (`owner = payer`, `pot = min(received, PUBLISH_MAX_POT)`, `transport hosted`, `published`, `tools`, `blurb`, `tier stone`, 0G keys) → `chain.createTopic` → `verified` → `fundVault` → `guarding` → Arkiv reconciles it with the real owner wallet. No castle row exists before the deposit (otherwise Arkiv would hand the listing to a placeholder owner).

**Hosted guard = data-driven business agent.** `lib/guardian/agents.ts` `businessAgent(castleId)`: fixture map first, else `castleRow` with `published && tools` → `fromRow` (tools: `{name, description, parameters, result?}`; the protected tool has no `result`). `prompt.ts`, `zerog.ts` and the verifier stay as they are and verify owner-published breaks exactly like Harshal's business agents. Validation in `lib/publish/schema.ts` (zod, shared with the form): tool name `/^[a-z][a-z0-9_]{0,63}$/` + `validProtectedTool`, 1–8 tools, exactly one protected (no result; the others must have a ≤2 KB result), orders 20–8000 chars, fee 0.1–10 ℏ, pot 1–`PUBLISH_MAX_POT` (100 ℏ), days 1–7, optional `payerAccount` (only that account's deposit counts), 0G key validated server-side. Orders, tool results and keys never appear in any response or log.

**Routes:** `POST /api/zg/validate`, `POST /api/castles` (no auth, ≤`PUBLISH_MAX_OPEN_DRAFTS` open drafts → 429), `GET /api/castles/[id]/deposit` (public status), `GET /api/castles/[id]` + `earnings {heldOps, ownerCut, potNow}` + `zg`, `close|open|vault-state` switch to `isOwnerOf`, `POST /api/castles/[id]/dry-run {text}` (owner; `transportFor(castleId).respond` with a `dryrun_` siege id; one model call on the owner's credits, no siege row) = "test your guard before anyone pays".

**UI:** `app/(arena)/publish/{page,publish-view}.tsx` (hall pattern), `components/publish/{tool-editor,live-card}.tsx`, steps GUARD → CONNECT 0G → MONEY → GO LIVE, the deposit panel, then `YOUR VAULT IS LIVE` (share link + QR, owner key shown once, RUN A DRY OP, OPEN VAULT PAGE). `lib/vocab` gets a `PUBLISH` table and `NAV.publish`; `top-bar.tsx` adds PUBLISH; the Grid's empty/CTA copy invites "Have an agent? Publish it as a guard." Vault page: earnings and credits lines in `OwnerPanel`, blurb + tool chips in `Identity`. The form copies `components/raider/create-agent-form.tsx`'s structure. A published guard's prompt also gets the chosen voice line appended (hash-neutral for fixtures, whose voice is "professional" with no line).

**Lane B files:** `lib/guardian/agents.ts` (DB fallback, additive), `lib/guardian/prompt.ts` (voice line for published guards), `lib/proxy/index.ts` (user billing), `worker/index.ts`, `worker/tick.ts`.

## 2. Part 2A — plug in your running agent (`@siege/guard`, J2)

**Shape:** the harness **long-polls us**, so it needs no public URL and no sockets. `GET /api/guard/next` (Bearer `gk_…`, `x-siege-lease: <uuid>`) blocks ≤25 s until a turn is pending, returns `{turnId, kind, siegeId, turn, messages}` or 204; `POST /api/guard/reply {turnId, reply, toolCalls}`; `GET /api/guard/hello` returns `{castleId, protectedTool, vaultState, openai: {baseURL: <app>/api/proxy/v1, apiKey: vk_…}, model}` and refuses `409 zg_not_connected` until the owner connected 0G. Newest lease wins; the loser's next poll gets `409 lease_lost`. The poll is the heartbeat (`last_seen_at` on every poll).

**Transport** `lib/transport/sdk.ts`: live lease → `enqueueTurn` in `guard_turns`, `awaitAnswer` (SQLite poll every 300 ms, 60 s timeout → `guardian_unavailable`, turn given back); no lease and stub mode → today's Penny canned path (keeps `npm run demo` 108/108 and the demo-script dev-endpoint walk); no lease on testnet → `TransportUnavailableError` (409 `not_guarding`). `move = open` when the reply's toolCalls name `protectedTool` **or** the proxy record for that turn has `protectedToolCalled`; `requestId` is resolved server-side from `proxy_records`, never trusted from the harness.

**Verification:** the harness's model calls go through our proxy with the stored `vk_` key (`vaultForKey` falls back to `castles.vault_key`; `issueKey` returns the stored key for SDK castles), and the proxy forwards them to 0G on the castle owner's key. The first proxied call during the self-check pins `castles.pinned_prompt_hash`; `lib/siege/verifier.ts` gets one branch: `transport === "sdk"` → compare `rec.promptHash` to the pinned hash (`no_pinned_prompt_hash` if null). A later different hash on a funded/guarding/dormant castle sets `prompt_drift_hash`; `worker/guard.ts` closes the vault with the existing `orders_changed` reason (pot back to the owner).

**Lifecycle** (`lib/guard/{keys,turns,lease,lifecycle,smoke}.ts`): created → connected (first poll) → self-check (one canned turn; we need a proxy record for it and the protected tool in the harness's tool list) → smoke op (3 canned override/authority/urgency turns as `kind smoke` guard turns, not a siege row; must hold all three) → verified → funded (deposit panel, or `/open` in stub) → guarding. `worker/guard.ts` every 1 s: expire stale turns, `guarding` + lease + no poll for 30 s → `dormant` (voids live ops, refunds), drift → close. Reconnect while dormant → guarding (in the route), re-running the smoke op when the lease changed.

**SDK + example:** `packages/guard-sdk` (`@siege/guard`, TypeScript, zero deps, tsc ESM + CJS): `createGuard({guardKey, baseURL, protectedTool, tools}) → {openai, model, serve(handler), stop()}`; `serve` runs the poll loop and sets `x-siege-id`/`x-siege-turn` per turn, replies with a canned apology if the handler throws so no turn is left unanswered, backs off on network errors, and prints the lifecycle as it advances. `examples/guard-refund-bot/index.mjs`: Penny with `lookup_order` + `issue_refund`, the `openai` npm client pointed at our proxy. The three demo lines are `createGuard`, `new OpenAI(guard.openai)`, `guard.serve(...)`. `scripts/seed.ts` provisions `gk_`/`vk_` for the Refund Desk if missing and prints `SIEGE_GUARD_KEY=…`. Owner-only `POST /api/castles/[id]/guard-key` rotates the key.

**UI:** `components/owner/plug-in-agent.tsx` (publish page branch): install snippet with the real key, six-LED strip CONNECTED → SELF-CHECK → SMOKE OP → VERIFIED → FUND → GUARDING polled from `GET /api/castles/[id]` (`Castle.sdk {leaseLive, selfCheckAt, smoke, promptPinned}`), failure reasons (`protected_tool_not_offered`, `smoke_failed_turn_k`, `self_check_no_proxy_call`), "last poll Xs ago". The vault page's existing "SDK · tool · heartbeat" line starts working because `last_seen_at` is now written; `/docs` carries the SDK README.

**Lane B files:** `lib/transport/sdk.ts`, `lib/transport/types.ts`, `lib/proxy/index.ts`, `app/api/proxy/v1/chat/completions/route.ts` (one header), `lib/siege/verifier.ts` (one branch), `worker/index.ts`, `worker/settle.ts` (+PERMANENT reason), new `worker/guard.ts`, `worker/dispatch.ts`, `lib/fixtures/raids.ts` (smoke template).

## 3. Part 2B — attacking agents: units and bring-your-own (J3, J4, J5)

**Units funded by the red teamer (J3).** `POST /api/agents` without the owner cookie → `unit_drafts` row + deposit intent (`kind unit`) + `rk_` operator key (once); requires a connected 0G key (same `zg-connect` component). The red teamer pays → handler `fundUnitFromDeposit`: `createAgent({…, budget: min(received, AGENT_MAX_BUDGET), owner: payer, operatorKeyHash, fundedBy: "operator", depositTx, zg keys})` (the arena creates and funds the unit's Hedera account with the amount it just received). `run|stop|approvals` accept the owner cookie **or** the unit's `rk_`; `GET /api/approvals` and the pager filter by operator key; `GET /api/agents/[id]` adds `balance` (mirror, 15 s cache), `zg` and usage. The owner-cookie path is unchanged (seed, demo, Night Sapper). `AGENT_MAX_COUNT` becomes 100, counting non-stopped units. `POST /api/agents/[id]/withdraw` (operator or owner; unit idle, nothing reserved) sends the unit's balance minus a fee reserve to the account that funded it (`transferFromUnit` reuses `topUpAgent`'s transaction pattern) and revokes the unit's 0G key.

**The unit is the red teamer's balance on the Grid (J4).** `POST /api/play/start` accepts `{castleId, agentId}` + `x-siege-operator-key`: the op is paid from that unit (`createPayerFetch(agentCredentials(id))`, caps via `checkCaps`) instead of the demo raider, so a hand-typed op's payout lands in the unit. The vault page's RUN OP button shows `PAY FROM <UNIT>` when a unit key is in the browser. Without one, today's demo-wallet path stays for QR visitors.

**Approvals on operator-funded units:** `per_castle|daily|stop_rule` → APPROVE raises the cap, moves no HBAR; `budget` → APPROVE returns a top-up deposit intent (`kind topup`), the approval stays pending until it lands, then budget += received and the unit resumes. Arena-funded units keep today's on-chain top-up.

**Compute on the red teamer's own credits.** `lib/proxy/agent.ts` `agentChat(req, billing)` routes to 0G with the unit's key and writes a `proxy_records` row with `billed_to = agent:<id>` (usage visible; never consulted by the verifier); `lib/agents/brain.ts` `nextAttackMessage({agent, castle, history})` uses the preset (`lib/agents/strategies/*.md`) or `strategyText` as system prompt and the transcript as context (model `ZG_AGENT_MODEL`); falls back to the scripted pools in stub mode; a rejected key pauses the run with a pager request `reason: zg_key` and the unit card shows `0G KEY REJECTED`. No HBAR is charged for compute. Arena-funded fixtures keep the team key.

**Security shipped with it:**
- Turn hijack: `POST /api/siege/start` returns `turnToken` (hash on `sieges.turn_token_hash`); `POST /api/siege/[id]/message` requires it (header `x-siege-turn-token`, Bearer, body, or the per-siege httpOnly cookie that `/api/play/start` sets); null hash → allowed (in-flight ops). Update `worker/agents.ts`, `scripts/demo.ts`, `scripts/golden-run.ts`, `qa/stub-op.mjs`, `lib/api/client.ts`.
- Unlimited recon: the free path on `/api/siege/start` requires `wallet = recon-<visitor>` plus an HMAC ticket minted by `/api/play/start`; `claimRecon` counts per visitor (`FREE_SIEGES_PER_DAY`), per IP (`FREE_RECON_PER_IP_PER_DAY` 25, venue Wi-Fi) and arena-wide (`FREE_RECON_PER_DAY_TOTAL` 400) in one transaction on `free_sieges`.

**Bring your own attacking agent (J5):** `examples/raid-bot/` (ESM; `@x402/core @x402/fetch @x402/hedera`; picks a guarding vault, pays the 402 from `HEDERA_ACCOUNT_ID/KEY`, five model-written or scripted messages with the turn token, prints the replay link; `x-siege-stub-payment` against a stub server), `qa/raid-bot.mjs` (`qa:bot`), `app/docs/page.tsx` + `docs/API.md` (sequence, headers, error codes, payout rules, limits, SDK README), recon briefing link `BRING YOUR OWN AGENT ▶`. `POST /api/operators {handle}` (rk-keyed) so the Hall shows handles instead of account ids.

**UI:** `create-agent-form.tsx` gains the custom-strategy textarea, the `zg-connect` field, the deposit panel and the operator-key reveal (stored in `localStorage siege.operatorKeys[agentId]`); unit card shows BALANCE / 0G CREDITS / funded-by / WITHDRAW; pager works with an operator key and renders a top-up deposit instead of APPROVE when the ask is `budget`.

**Lane B files:** `lib/proxy/agent.ts` (new) + `lib/proxy/index.ts` export, `worker/agents.ts`, `worker/dispatch.ts`, `lib/pay/{caps,approvals,free}.ts`, `lib/db/schema.ts`.
